# 1k: platform follow-ups after rewrite mode

Verdict: the glibc guests now run on the non-AVX dev VM (hello, threads, clone, signals, Go; the runner's own libc.a executes AVX at start-up, so the guests are built in a Debian container, and text pieces that begin inside an instruction no longer corrupt the code), the stub start-up and Release waits are bounded, stale per-site entries are dropped on unmap, and the rare hang is reduced from 9 in 48 (before the earlier fix) to 2 in 100 but not gone; veneer islands, stub recycling and the rewrite-mode engine stall are not done.

## 1. glibc on a CPU without AVX

Cause (disassembly of the dev VM's `hello`, `init_cpu_features` at 0x403090): the static glibc of the CI runner is built with VEX encoding throughout (vzeroupper in cold paths, `vmovd`/`vpinsrd` in the CPU-feature init itself, 245 non-ifunc functions with VEX instructions in `hello`), so it cannot run on a CPU without AVX whatever CPUID says. Not the platform: CPUID runs natively and XCR0 is never involved. Fix: `test/guests/build-glibc.sh` builds every glibc guest (and the busybox of the guests) in `debian:bookworm` (baseline x86-64 glibc 2.36) in the `windows-sentry-guests` and `windows-runsc` workflows; the dynamic guests' libraries come from the same container. All legs of the guest suite pass with them.

A second dev-VM-only bug showed up once `hello` got past start-up: a text range that begins inside an instruction (here a `lea` straddling 0x43e000, the pieces are mapped separately) was decoded from its first byte, so garbage "instructions" at the start were treated as windows and a syscall patch overwrote the first byte of the real `mov $0xda,%eax` (fault at 0xffffffff83d496d0 in `__tls_init_tp`); in Go guests a `mov %fs:-8,%r14` after a straddling `xorps` was swallowed by a garbage `jmp *` and never rewritten (SIGSEGV at 0xfffffffffffffff8, which also explains some "lost %fs base" reports). Now: the original last 16 bytes of every scanned piece are remembered and the next piece is decoded starting in them (`tails`); sites in the first 8 bytes after such context, or in the first 48 bytes of a piece without context (the piece below may be mapped later), only get the safe patch (`ud2`, run by the debugger). `TestFSInstructionAfterSplit` covers the split.

Dev VM (QEMU, no FSGSBASE/XSAVE/AVX), `runsc --network=none run` with bundles under `trylocal`, commit 0c354f20 plus the diagnostics commits: hello (exit 7, "hello from glibc: argc=1 tv=5 work=10 heap=ok"), threads (`counter=160000 idsum=28 main_tls=1`), clonesys, signals segv, gostress (Go) all pass. Dynamic glibc guests and the busybox applets of the new Debian rootfs could not be run there from a host folder: ld.so reports "libc.so.6: file too short" when the library is read from the host folder (static ones from the same folder work); that is a gofer/host-folder problem, not the platform. busybox from the earlier Ubuntu build ran on the VM before.

## 2. The rare hang

Evidence from the dumps of the 100-run loop (`windows-profile`, exclusive root cache): two shapes, a task in `newAS` waiting for the anchor thread of a new stub, and a task in `Switch` waiting for a thread that never published (the state dump added here shows such a thread parked after an instruction-fetch fault at `trampPark`'s first instruction, not suspended, 0 cycles in 300 ms: the redirected thread is not scheduled). Changes: `debugLoop` waits at most 100 ms and ends when the address space is released or the process is gone; `Release` abandons a stub (leaks process, goroutine and handles) if the loop does not end in 10 s; the anchor wait is 5 s, then `NewAddressSpace` tries again, up to three times; a stub thread that has not run after 3 s is terminated and created again; the hang dump includes `DumpState`. Handle audit: `Release` closes `evReq`/`evReply` of every slot and `hThread` of slots other than 0 only if non-zero, `freeThread` zeroes `hThread` after closing, `hMain` and `as.h` once; the debug-event file handles are closed once. No double close found. The stub image is written once per runsc process (`Platform.New`), not per stub.

Result: exclusive root cache 98 of 100 pass (before: 97 of 100 at the earlier fix, 39 of 48 originally), shared 16 of 16. The remaining hang is the unscheduled-thread shape above; not understood. The suggested capture without SuspendThread is not implemented.

## 3. Not done

- Veneer islands/near areas for high-mapped code and more veneer room (`platform-fs-veneer-capacity`): the design needs a reserved region near each high mapping (the main PIE of a Rust binary is far from the libraries), not started. The low area was moved up by 0x10000 earlier (0xC0000..0x200000) and the veneer area is 448 KiB.
- Stub recycling (`platform-recycle-stubs`): not started.
- The rewrite-mode Podman stall (`platform-rewrite-mode-slow-engine`): not diagnosed. The state dump now counts debug events, `%fs` instructions run by the debugger and stops moved out of veneers per address space; one such dump from the stalled engine says whether the debugger path is hit constantly. Suspects: the 48-byte safe zone (new, makes sites near piece starts use the debugger, but only a handful per piece), veneer-area exhaustion for large images, interrupt-heavy Go preemption inside veneers.
- Stale entries: `restartAt`, `ud2Sites`, `fsUD2` and the saved tails are dropped when text is unmapped (`purgeSites`); the slot and veneer caches are content-keyed and stay. No test of an address reused with different code.
